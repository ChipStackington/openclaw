# RR-1 repair design — separate complete installation guard

The v1 dist/pi-ai material reader stays unchanged: no links, at most 20,000 files. The new guard is a separate versioned installation contract, not another v1 material inventory.

## Contract and membership

One immutable physical installation root contains the complete engine runtime: compiled dist, package and lock metadata, patches, all of node_modules/.pnpm, package aliases, plugins, native addons, WASM, provider assets and lazy dependency branches. There are no extension-based or toolchain-package exclusions within this root. Source/test/build-tool files present in that installation are also measured. The manifest and startup configuration live outside it; mutable evidence, credentials, sessions, logs and legal state must live outside it. The manifest lists every physical directory (including empty directories), every regular file with size/SHA256, and every link with its direct root-relative target, resolved physical target and file/directory kind. Enumeration never descends through a link. Every alias must resolve inside the same installation root to inventoried physical material. External aliases, cycles, special files, hardlinks and linked root ancestors are refused.

The separately bounded guard permits 200,000 regular files / 400,000 total entries, 64 MiB manifest metadata, depth 64, 1 GiB per streamed file and 16 GiB total material. Files are streamed in 1 MiB buffers. Bootstrap/candidate inventories with at least 256 physical files use four bounded built-in-only hashing workers, with a 600-second hashing limit. Workers verify initial/opened/final/named file metadata against the main scan, inherit no preload arguments, and import no engine/provider code. Fixed-size shared hash/status buffers avoid per-file message queues. The guard is published only after every worker succeeds, every approved digest matches and the second complete metadata scan succeeds. Worker failure/timeout refuses startup; no boundary deadline is increased. Smaller graphs and loaded files use the same synchronous before/opened/after/named hashing checks. These bounds cover the disclosed 129,027-file/3.36 GB graph without relaxing the original material reader. A release exceeding these guard bounds is held; it cannot truncate or auto-select a smaller graph. A reviewed root excludes no runtime-resolvable files by policy.

## Startup and loaded bytes

Legal startup configuration becomes version 2 and requires installationRoot, installationManifestFile and installationManifestHash. The launcher must preload the dedicated built-in-only compiled guard entry before importing engine code, with NODE_DISABLE_COMPILE_CACHE=1. An active compile cache is rejected so unmeasured cached bytecode cannot substitute for pinned source. Node must support synchronous registerHooks (verified runtime Node 24.14.0). The operator must verify this bootstrap and the Node executable/platform separately; self-measurement is not a trust root. The preload verifies all material before publishing a process-local frozen guard. A synchronous Node resolve/load hook confines ESM/CommonJS module resolution to inventoried physical installation files (plus Node builtins), verifies pinned file bytes and metadata at each load, and verifies returned JavaScript/JSON source bytes. Unsupported source-less formats are held except native addon loads, whose files are inventoried and verified. Lazy modules are covered even when never previously loaded. No observed trace is used as a substitute for full graph membership.

Startup requires the real preload guard and matching configuration digest. A missing guard, old version-1 configuration, incompatible Node hook API or outside runtime module fails before listener creation. All production actual module paths must belong to the same guarded installation. No client can inject pins, paths or a guard. The loaded process cannot silently select a different installation/configuration. Trusted host operation is assumed; this is material provenance/drift protection, not protection from a privileged attacker replacing the Node runtime, altering process memory or disabling its own hooks.

## Boundaries and identity

Every existing synchronous capability, capture creation/start, pre-send and final seal runtime check invokes the same guard. Bootstrap enumerates and hashes the complete installation and captures its physical metadata only after exact approved-manifest readback. Every later boundary enumerates the complete physical tree and rechecks every file, directory and alias against that immutable process baseline, followed by a second metadata/topology pass. It does not reread 129,027 dependency files at every boundary. Bootstrap and each module load open/hash files and compare file identity/metadata before and after read. Boundary metadata includes device, inode/file identity, mode/type, link count, size, nanosecond modification and change times; aliases also bind their direct and final realpath targets. The original process baseline never advances or self-approves changed material. Ordinary writes, replacements, timestamp-preserving copies, links and change-and-restore are held. These metadata checks rely on trustworthy filesystem change metadata; a host actor able to forge it or alter the guard/process is outside this provenance contract. No claim of cryptographic rereading of unchanged non-module assets at each boundary is made. Any installation guard or guarded module-load failure permanently latches that process unavailable. Existing configuration/role drift remains a separate runtime check. A clean source restoration requires a fresh verified process, never a refund/retry of a consumed evidence reservation.

The existing RuntimeIdentity schema remains unchanged. engineBuildHash becomes a domain-separated v2 hash of engineRevision, measured dist inventory and complete installation manifest digest. Old v1 dist-only pins therefore cannot approve the guarded runtime. The independent app registry and installed mapping remain empty/unapproved; generating a candidate manifest does not approve it. Configuration and external manifest bytes are rechecked at each boundary. Existing pi-ai package/version/content and patch checks remain.

## Explicit exclusions and performance

Node executable/builtins, Windows/system libraries, external operator tools, process environment and mutable external credentials/state are outside this installation contract and require independent operator/platform gates. No package inside the physical installation is excluded as a development tool. Dynamic module loads outside the installation are refused, including globally installed tools/plugins. External child-process execution is not made into a module provenance guarantee by Node hooks.

The first conservative full-byte-at-every-boundary candidate is retained separately: its fresh full material census was still progressing after nine minutes and is unsuitable for normal operation boundaries. The revised complete installation guard uses full bootstrap/load byte checks plus complete immutable-generation metadata checks at every boundary. Fresh realistic bootstrap and boundary timing must be reported. Existing deadlines and accounting caps cannot be increased to accommodate it; if realistic checking cannot complete within those limits, readiness remains held and performance design needs independent review. No actual provider request, installed adoption or platform acceptance is needed to test the source repair.
